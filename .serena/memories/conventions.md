- `LiteService` is a manual singleton (`private static final LiteService INSTANCE = new LiteService()`, `getInstance()`) — all business logic and raw JDBC live here, not in DAOs (the old `dao/` package is dead code, see `mem:core`).
- DB access pattern: `try (Connection con = db.getConnection()) { ... }` (try-with-resources) inside each `LiteService` method — no connection pooling/DI framework.
- Multi-step writes wrap in `con.setAutoCommit(false)` + explicit commit (e.g. `createOrder`). Contention-prone row updates use `WITH (UPDLOCK, ROWLOCK)` (e.g. order status transitions, table transfer, cup-count decrement) to prevent race conditions from two devices acting on the same order/table simultaneously.
- Order status is a strict one-directional state machine enforced server-side in `LiteApiServlet.canSetStatus`: `Pending -> Preparing -> Ready -> Served -> Paid`, with `Paid -> Cleared` handled separately via `/tables/clear` (not `/orders/status`). Backend re-validates every transition regardless of frontend state — never assume frontend-only validation is sufficient when adding a new transition path.
- Role naming mismatch: the "waiter"/"bồi bàn" role is called `runner` internally in code (session role value, DB, JS filenames like `page-runner.js`) but shown as "Waiter"/"Bồi bàn" in UI/docs — don't be thrown by the naming gap.
- Role-based access is enforced in TWO layers: `SecurityFilter` (page + API allowlists per role, `isPublicApi`/`isAllowedApi`) server-side, and `nav(role)` in `i18n.js` client-side (hides UI only, not a real security boundary). When adding a new API/page, both layers usually need updating.
- i18n: all UI strings live in a `dict` object (`vi`/`en`) inside `web/assets/js/i18n.js`; language stored in `localStorage` (`coffeshop_lang`). Every page defines `window.renderPage` so `i18n.js` can re-render dynamic content on language toggle — static HTML text alone won't update.
- JSON handling is hand-rolled (`JsonUtils`), not a real parser — keep payloads to the simple Map/List/String/Number/Boolean shapes it supports.
- Frontend has no build step; JS/JSP files are edited directly and served as-is.
